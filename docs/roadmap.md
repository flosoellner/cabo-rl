# Roadmap

Living document. Checked items are built and verified; the rest is sequenced future work.

- [x] **0. Repo + app scaffold.** `reference/` (untouched originals), `web/` (the shippable PWA), `python/` (the research pipeline), `docs/`.
- [x] **1. Python rules engine + info-set enumeration.** [`python/cabo_rl/rules.py`](../python/cabo_rl/rules.py) is a faithful port of `engine.ts` (the current, rule-correct implementation — not the stale `cabo.py`), covering deck construction, the multi-discard equality-against-each-other rule, all three power bands, the Cabo lockout, kamikaze, and scoring/reset-at-100. [`python/cabo_rl/enumerate.py`](../python/cabo_rl/enumerate.py) replaced the hand-wavy complexity estimate with real numbers — see [`docs/complexity.md`](complexity.md).
- [x] **App shell shipped.** `web/` + a real PWA layer (manifest, icons, service worker) — installable on a phone home screen, works offline.
- [x] **First real agent shipped, replacing the tabular Q-agent entirely.** Out of order relative to the plan below (NFSP was meant to come first) - this was a deliberately lighter first cut: self-play with Monte Carlo returns (every decision in a round gets that round's real outcome as its target, same idea as the old agent's `agentLearn`, just with a neural net instead of a table and covering *every* decision, not 3 of them) rather than full NFSP. Trained on a temporarily-downsized single-round variant (same 0-13 value range, hand size, and rules - just 2 copies of each card instead of 2-4), then rescaled to the real 52-card deck once the approach was validated.
  - `python/cabo_rl/features.py` / `net.py` / `agent.py`: belief-distribution state encoding (not scalars), one shared trunk, a permutation-invariant position scorer for every "which position" decision.
  - `python/cabo_rl/export_onnx.py`: exports to a single self-contained `.onnx` file, verified 0 argmax mismatches against the PyTorch original across 20,000 random probes.
  - `web/src/netFeatures.ts` + `web/src/netAgent.ts`: TypeScript port of the feature encoding + an async ONNX-driven turn runner (onnxruntime-web, vendored into `web/public/ort/` since this project has no bundler), replacing `engine.ts`'s Q-table agent calls entirely. `app.ts`'s agent-turn logic is now pluggable (`setAgentTurnRunner`) so `test_app.mjs` can mock it under plain Node instead of needing a real WASM/ONNX environment.
  - **Two real bugs found via direct testing, not caught by any automated test**: (1) a severe position bias - every "which position" decision used a plain per-index head, and since the game only lets you look at your first 2 cards at the round's start, training data was skewed toward positions 1-2; measured 50% accuracy overall, 19% specifically for position 4. Fixed by scoring each candidate position with one shared small MLP instead of a per-index head (permutation-invariant by construction) - 97% after, uniform across positions, with fewer training episodes. (2) the network was never told the *value of the card it was currently deciding what to do with* - `decide_place_or_discard` and the swap-target decision received `card` as a parameter but it was never threaded into the feature vector, so those decisions were structurally incapable of reacting to what was actually drawn. Both are why "agent sucks" turned out to be true and diagnosable rather than just needing more training.
  - Known remaining gap: kamikaze (`{12,12,13,13}`, the single best hand in the game) is still never called correctly - too rare in random self-play to have been learned incidentally. Not yet fixed.
- [ ] **2. Vectorized/batched self-play env** (PyTorch, MPS-accelerated on this machine). Thousands of parallel games per training step — needed before real NFSP/Deep CFR-scale self-play is feasible; the current agent trains one game at a time (~150k episodes in ~11 minutes on this machine, fine for Monte Carlo returns on a 4-card-hand game, not fine for what comes next).
- [ ] **3. Richer state representation.** A small GRU/transformer over the public action history, plus explicitly-engineered opponent-modeling features (e.g. "spied position *i*, then didn't blind-swap it" — see the project's opponent-modeling design notes). The current belief-distribution + permutation-invariant encoding is a real step in this direction but has no history/memory of the game so far beyond what's baked into the current state.
- [ ] **4. NFSP.** Best-response DQN + average-strategy supervised network, trained via self-play *league* (not one frozen opponent) to avoid non-transitive strategy cycling. The shipped agent is NOT this - see the note above.
- [ ] **5. Exploitability evaluation.** Win-rate against `RandomPolicy` (what's used for now) is a weak signal - `RandomPolicy` frequently sabotages itself. Need an approximate best-response oracle (train an adversary against a frozen candidate policy) for the full game, and exact backward induction on the shrunk variant from step 1 to cross-validate the approximate methodology.
- [ ] **6. Deep CFR** track.
- [ ] **7. ReBeL** (public-belief-state search). Most engineering-heavy, most SOTA — a stretch goal built on top of a working, evaluated NFSP baseline, not attempted before one exists.
- [ ] **Fix kamikaze.** Either oversample it during self-play (deliberately deal it occasionally rather than waiting for it to occur naturally) or hand-code it as a rule the learned policy can't override, similar to how `use_group_discard`'s candidate group is found deterministically rather than learned.

## Why this order (original plan vs. what actually happened)

The original plan was NFSP before Deep CFR before ReBeL, with the ONNX/browser bridge (old steps 8-9) coming *after* a real algorithm existed. In practice, direct pressure to "just implement something better than what we have now" moved the ONNX export + browser wiring earlier, paired with the simplest thing that could plausibly work (self-play + Monte Carlo returns) rather than waiting for NFSP. That infrastructure (export_onnx.py, netFeatures.ts, netAgent.ts) is now reusable as-is for every future checkpoint - swapping in an NFSP/Deep CFR/ReBeL-trained model later is a re-run of `train.py` + `export_onnx.py` + copying one file into `web/public/models/`, not new engineering.
